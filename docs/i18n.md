# Translations

> **Status in 0.1.0-beta.1:** The machinery on this page is built and held by
> tests: the id-based catalogues, the language manager, live switching,
> right-to-left mirroring and the language list in Settings
> (`SettingsScreen.qml`). The translations are not finished: German, French,
> Spanish, Japanese, Simplified Chinese, Hebrew, Arabic and Yiddish are
> complete machine drafts (all 460 strings, including the 42 that the N x N
> app added) that no fluent reader has been through; the app shows them.
> Some literals in the interface still do not ask for their words by id and
> stay in English in every language ([`i18n-lanes.md`](i18n-lanes.md) lists
> them: 75 at the time of writing).

How Cubeulator is made translatable, and how it is kept that way. This is the
plumbing (workstream E2b of [the app experience plan](app-experience-plan.md)).
The translations themselves are E5's; the wording they translate is
[`design/content.md`](design/content.md) and
[`design/strings.json`](design/strings.json). German, French, Spanish, Japanese,
Simplified Chinese, Hebrew, Arabic and Yiddish have a first, machine-assisted
draft that no fluent reader has been through: see
[German, French and Spanish](#german-french-and-spanish-the-drafts),
[Japanese and Simplified Chinese](#japanese-and-simplified-chinese-the-drafts)
and [Hebrew, Arabic and Yiddish](#hebrew-arabic-and-yiddish-the-drafts).

The set at first release is **nine languages**: English, German, French,
Spanish, Japanese, Simplified Chinese, Hebrew, Arabic and Yiddish. Three are
written right to left. The source language is British English.

## How it fits together

```
docs/design/strings.json          id, British English, note for translators, plural forms
src/app/i18n/languages.json       the nine languages, their plural forms, their direction
        |
        |  tools/i18n/strings_to_ts.py --write
        v
src/app/i18n/translations/cubeulator_<file>.ts      one id-based catalogue per language, committed
        |
        |  lrelease -idbased -nounfinished   (src/app/CMakeLists.txt, cube_app_i18n)
        v
:/i18n/cubeulator_<file>.qm       embedded in the app
        |
        |  cube::i18n::LanguageManager (src/app/qt/i18n/)
        v
qsTrId("some.id") in QML          what a person reads
```

`<file>` is the `file` field of `languages.json`: the code with an underscore,
`zh_CN` for `zh-CN`. There are ten catalogues, the nine languages and the
pseudo-locale `xx`.

- **`strings.json` is the only place a string is written.** Its ids, English,
  notes and plural forms are copied into every catalogue by
  `tools/i18n/strings_to_ts.py`; the CTest entry
  `i18n_catalogues_match_strings` (so every CI leg) fails if a catalogue is
  not what that script would write. A translator's work is kept: the script
  merges by id and never writes a translation of its own.
- **Strings are keyed by id**, not by their English (`family.md` D5). Rewording
  the English does not touch a translation. A string whose *meaning* changes
  gets a new id.
- **English is installed under every language.** A string with no translation
  yet - none in the eight drafts today, but any string added after they were
  written will be one, and so will every string of a language added before E5
  has been to it - shows its English. That is also what makes "a raw id on the
  screen" impossible for any id the catalogue has, and a test holds it (below).

## Writing a string in QML

```qml
Text { text: qsTrId("home.lede") }                         // a whole string
Text { text: qsTrId("home.resume.body").arg(turn).arg(total) }   // "Turn %1 of %2"
Text { text: qsTrId("review.status.partial", count) }      // a plural: "%n sticker to go"
```

- **Always `qsTrId("id")`, with a literal id.** Not `qsTr`, not a string
  literal, not an id built from pieces: the extractor, the lint and the tests
  can only see a literal.
- **Whole sentences.** Never `"Turn " + n + " of " + total`: a translator
  cannot reorder fragments. One string, `%1` and `%2` where the numbers go.
- **Wording belongs in QML, never in a controller.** A controller exposes a
  state or a code; QML says it (plan, "Contracts every lane keeps").
- **Capitals are the app's job.** A small-capital label is written in
  sentence case in `strings.json` and given `font.capitalization:
  Font.AllUppercase`, which is locale-aware.
- **Direction words never mirror** (`dir.left` is the physical left): do not
  swap them for a right-to-left language.

### Numbers, dates and times

The app's language sets the default `QLocale` (the operating system's does
not), so digits, separators and date formats follow the language the person
chose. In QML read the locale through `Qt.uiLanguage`, which makes the binding
update when the language changes:

```qml
Text { text: Qt.locale(Qt.uiLanguage).toString(AppState.moveCount) }
Text { text: Qt.locale(Qt.uiLanguage).toString(date, Locale.ShortFormat) }
```

In a plural string the count is written `%Ln` in the catalogues (`strings.json`
keeps `%n`; the script converts), which Qt formats with that locale. Arabic
shows Arabic-Indic digits; notation letters, key names and version numbers
never go through it.

## Adding a string

1. Add it to `docs/design/strings.json`: `"group.name": ["English", "Note for
   the translator"]`. A plural is `{ "one": "...", "other": "..." }` with `%n`.
   Say in the note where it appears and what a placeholder is.
2. `python tools/i18n/strings_to_ts.py --write` and commit the ten `.ts`
   files (nine languages and the pseudo-locale) with it.
   `python docs/design/tools/build.py` regenerates the inventory in
   `content.md` and the prototype from the same file, and
   `python docs/design/tools/check_design.py` fails on a string that no
   design page names. Neither is run by CI, so run them.
3. Use it: `qsTrId("group.name")`.

To remove a string, delete it from `strings.json` and rerun the script; git
keeps what a translator wrote. To reword, edit the English in place. To
change what a string *means*, add a new id.

## Adding a language

1. Add an entry to `src/app/i18n/languages.json`: `code` (what is stored under
   `language/code`), `file`, `tag` (the `QLocale` name), `name` (the language
   in itself, never translated), `plurals` (the number of plural forms Qt's
   rule has for it - `lconvert` tells you, the table below shows the nine),
   `rtl`, `translated: false`.
2. `python tools/i18n/strings_to_ts.py --write`. The new catalogue,
   `src/app/i18n/translations/cubeulator_<file>.ts`, is made with every entry
   unfinished; the app shows English for all of it.
3. Give its script a face. `Theme.qml` chooses the face by language and
   today does so only for Japanese and Chinese (`fontHeading`, the system's
   own); every other language is asked for Archivo, which is not bundled in
   this tree, so a machine without it falls back to whatever it has (see
   "What belongs to other branches"). Right to left is read from `rtl`; a
   test fails if it disagrees with Qt.
4. Teach the tests that name the set: the lists of codes and names in
   `tests/i18n/language_manager_test.cpp` and the plural-rule table in
   `tests/i18n/translation_runtime_test.cpp` fail until the language is in
   them.
5. The translator fills the catalogue in Linguist or by hand. "Unfinished" is
   Qt's word for an entry with no translation yet
   (`<translation type="unfinished">`): it is left out of the compiled `.qm`,
   so the English shows, and finishing the entry in Linguist removes the
   `type`. Linguist writes the file in its own layout, so run
   `strings_to_ts.py --write` afterwards; the CTest gate compares against it.
   There is no `lupdate` step: `strings.json`, not the source, is where
   strings are written, and `strings_to_ts.py` keeps what a translator has
   done. (`tools/i18n/check_ids.py` runs `lupdate` only to read which ids the
   code asks for.)
6. A catalogue that is whole but has not been read by a fluent person is a
   **draft**:
   `"draft": true` in `languages.json`, `translated` still `false`; it is
   shown in the app like any finished entry, and `strings_to_ts.py --status`
   says so. When a fluent reader has been through it, drop `draft` and set
   `translated: true`: from then on the translation tests require no
   unfinished entry in it.

|---|---|---|---|---|---|
| `en` | English | 2 | ltr | Archivo | the source |
| `de` | Deutsch | 2 | ltr | Archivo | **draft** |
| `fr` | Français | 2 (0 and 1 are the singular) | ltr | Archivo | **draft** |
| `es` | Español | 2 | ltr | Archivo | **draft** |
| `ja` | 日本語 | 1 | ltr | the system's, chosen by language | **draft** |
| `zh-CN` | 简体中文 | 1 | ltr | the system's, chosen by language | **draft** |
| `he` | עברית | 2 | **rtl** | the platform's, by fallback (the design's is Noto Sans Hebrew) | **draft** |
| `ar` | العربية | 6 (zero, one, two, few, many, other) | **rtl** | the platform's, by fallback (the design's is Noto Sans Arabic) | **draft** |
| `yi` | יידיש | 2 | **rtl** | the platform's, by fallback (the design's is Noto Sans Hebrew) | **draft** |

`strings_to_ts.py --status` is the live count; "draft" is `languages.json`'s

Qt's table gives Hebrew two forms (one, other); CLDR also has a dual. The
catalogue carries what `lrelease` will use, and the dual is said in the
plural's other form.

The face column is the design's (`design/platforms.md`, "Fonts"). In this tree
only the Japanese and Chinese rows are what the app does: Archivo, IBM Plex
Mono and the two Noto faces are not bundled yet (the browser build bundles
only its Japanese and Chinese subsets), so a machine that does not have
Archivo draws Latin, Hebrew, Arabic and Yiddish in whatever it falls back to.

## What a translator needs to know

- **Where**: `src/app/i18n/translations/cubeulator_<file>.ts`, one `<message
  id="...">` per string. The id is the key and never changes once a
  translation exists for it. The English (`<source>`) and the note
  (`<extracomment>`, shown as a comment in Linguist) are context, and the note
  says where the string is shown.
- **`%1`, `%2`** are arguments and may be reordered. **`%Ln`** is a count and
  the string has plural forms: supply every form the language has.
- **Never translated**: *Cubeulator*, the notation letters, key names.
- **Whole sentences**, no joining. The three parts of a turn are shown as
  three labels and are the one exception (`content.md`).
- **Design allows 40% more than the English.** The pseudo-locale takes all of
  it, so a layout that holds there holds a real translation.
- **Right to left**: write *left* and *right* as the physical left and right.
  The app does not swap them.

## Japanese and Simplified Chinese: the drafts

`ja` and `zh-CN` were written on 2026-10-14: all 406 entries, every plural in
the one form each language has. They are **machine-assisted drafts that no
fluent reader has been through.** They have not been tested against a real
cube held yellow on top and green in front, which `content.md` asks of the
colour, side and direction words ("they are the product"). Until that
happens:

- `languages.json` says `translated: false, draft: true`. The app shows the
  translations: that is the point of a draft. It does not yet say that they are
  unreviewed to the person reading them; the in-app machine-translation note
  under the language list is E5's (`family.md`, "Cubeulator is behind in
  these"), and ICL Forge and Countdown Solver say it there. This page, the
  changelog and the pull request are where it is said for now.
- Nothing requires a draft to stay whole. A string added to `strings.json`
  after the draft shows its English in Japanese and Chinese until someone
  translates it (`strings_to_ts.py --status` counts). Setting `translated: true`
  after review turns that into a failing test.

browser build has no system fonts and carries Noto Sans JP and SC subsets
(`src/app/platform/web/fonts`), which must hold every character of the
catalogues: `i18n_web_cjk_subsets_cover_catalogues` fails when a translation
brings in one they lack, and `tools/fonts/subset_cjk.py --write` is the fix.

## German, French and Spanish: the drafts

`de`, `fr` and `es` were written on 2026-10-14: all 418 entries, every plural in
the two forms each language has (French counts 0 and 1 as the singular). Like
the Japanese and Chinese ones above they are **machine-assisted drafts that no
fluent reader has been through**, on the same terms: `translated: false,
draft: true` in `languages.json`; shown in the app like any finished entry; no
in-app note yet (E5's); a string added to `strings.json` later shows its
English in every draft until someone translates it. They have not been held
against a real cube either (`content.md`: colour, side and direction words "are
the product").

**What to check first.** The register is a choice, not a fact: **du**, **vous**
and **tú**, the imperative of each. A reader who would rather the app used
*Sie*, *tu* or *usted* is changing every instruction in the file, which is why
it is said here and not left to be found.

The layer is numbered from the side a turn is named by (`שכבה 2`, `الطبقة ٢`,
`שיכט 2`; the number arrives through `%2` in the locale's digits), the word the
stage explanations already used. *Set up* is not *הכנה* / *التجهيز* / *גרײטן*,
which are `stage.reduce.title`. The entry screen's English says *moves* where
the glossary says *turn*; the settings text already speaks of turns written as
letters, so the draft keeps the one word. For a reviewer to look at first:
Hebrew *קצוות* and *מרכזים* as the stage titles; Yiddish *ראַנדן* and
*צענטערס* as plurals (the Germanic *-s* on a loanword), which are the
translator's guess; Yiddish has no settled cubing vocabulary, so *צומישונג*
("the mixing-up") for the scramble is a description and not a term; Arabic
*تسلسل الخلط* ("the mixing sequence") for the same reason.

How each is addressed: Hebrew in the plural imperative (*סרקו*) and the
infinitive for dialog choices (*למחוק*, *להשאיר*); Arabic in the masculine
singular imperative, unvocalised except where the word would otherwise be read
as another (*حُلّ*); Yiddish in the plural imperative (*דרײט*), YIVO
orthography. The one button that speaks in the first person
(`solve.hold.ready`, "I am holding it like this") is kept off Hebrew's gendered
forms: *הקובייה מוחזקת כך*. Arabic's *دورة* is also "a rotation", which is why
the quarter and half turns read *ربع دورة* and *نصف دورة*.

**Right-to-left text, and what the catalogues carry for it.** A catalogue holds
only characters of its script, Latin, digits, the middle dot, the
multiplication sign (a size of cube, `5×5`), the ellipsis and two marks, and a
test holds it to that (`[script]`). It allows ASCII punctuation and no curly
quotes, so a quoted word is written in straight `"` quotes:

- **U+200E (left-to-right mark) after a run that ends in a neutral
  character** and that must not be reordered: the cube notation in
  `settings.notation.note` and `solve.a11y.notation` (`R U R'`). Without it the
  apostrophe lands on the wrong side of the letter in a right-to-left line.
- **U+200F (right-to-left mark) first in a string that opens with a Latin
  word** (the product name). Qt Quick `Text` takes a string's direction from
  its first strong character: "Cubeulator ..." with nothing before it is laid
  out left to right, its words come out in the wrong order and it sits against
  the wrong edge (seen in the browser build, in the camera sentence of
  Settings). A test holds it (`[bidi]`): a right-to-left string whose first
  letter is Latin must start with the mark. `app.name` and `licences.own`,
  which are the name and not a sentence, are the exceptions. The test strips
  the placeholders first, so it cannot see that `entry.error.unknownMove` and
  `entry.error.layer` open with `"%1"`, where `%1` is the move the person typed
  and so Latin at run time: both start with the mark all the same, by hand.
  `entry.scramble.help` has the other kind, a U+200E after `U'` (a letter and
  an apostrophe, then right-to-left text).
- **Digits follow the locale.** Counts go through `%Ln`, so Arabic shows
  Arabic-Indic digits (Qt's `ar` is Egyptian Arabic and writes them) and Hebrew
  and Yiddish Latin ones. The numbers written into an Arabic string (`من ٦`,
  `٤٨`, `١٠٠`) are Arabic-Indic too, so that a line does not mix the two; the
  names of things that are not quantities stay as they are: the cube's `3x3`,
  the licence's version 3, the notation's `2` and the key names. The size
  buttons (`entry.size.option`, `%1×%1`) get the locale's digits, so an Arabic
  button reads `٥×٥`, while the sentence under them names the 3×3 in Latin
  digits as every other mention of it does: a reviewer may prefer one or the
  other on that screen.
- **Yiddish digraphs are single characters** (U+05F0-05F2, double vav, vav yod,
  double yod), and letters and points are separate characters: the generator
  never leaves a presentation form (U+FB1D-FB4E) in a catalogue.

**Added 2026-10-17 (the N x N app, [`nxn-app-plan.md`](nxn-app-plan.md)).** The
42 strings its size picker, scramble entry, hand entry, stage names, layer
words and history rows needed, 460 entries in all, on the same terms as the
rest and with the rules above applied: the new rows of the table and the notes
under it are what to look at first. None of the 42 is a plural.

**The macOS menu wording** (`menu.*`) follows Apple's Hebrew and Arabic as the
translator remembered it; nobody has checked it on a Mac. macOS has no
Yiddish, so those are the translator's own. The developer-build strings
(`settings.dev.*`, `diagnostics.*`) are translated too, although their notes
say they may stay in English.

**Reading them.** `CUBE_I18N_SHOT_LANG=he` (or `ar`, `yi`) with the `[.shots]`
case below puts a screen in front of the reviewer; in the browser build
`window.cubeulatorEnvironment = { CUBEULATOR_LOCALE: 'he' }` (the environment
the page hands the app) does it. Only the converted screens are translated
(`i18n-lanes.md`): the solve, scan and review screens show English until their
lanes convert them.

**Fonts.** None of the three scripts has the Japanese-and-Chinese problem of
one set of code points drawn in another language's forms, so the app does not
choose a family by language here: `Theme.fontHeading` is Archivo, which is
installed nowhere yet, and the text falls back to the face that has the script
(Segoe UI on Windows, the system's on macOS, DejaVu Sans or Noto on Linux). The
design's faces (Noto Sans Hebrew and Noto Sans Arabic, `platforms.md`, "Fonts")
are the kit's to bundle with Archivo.

The browser build has no system fonts and was the one to check. Qt for
WebAssembly draws Hebrew, Arabic and Yiddish with the face it bundles, DejaVu
Sans (2026-10-14, headless Chromium, the three languages at 960 x 680 and
390 x 844): no boxes; Arabic is joined and shaped (the vowel marks the draft
uses, the Arabic comma and question mark); Yiddish points (pasekh, komets,
rafe, dagesh, khirik) and digraphs sit where they belong; a heading's weight
800 is DejaVu's bold. So **no subset is bundled for them**, unlike Noto Sans JP
and SC: a Noto subset used only for Hebrew and Arabic would set a string in two
faces, DejaVu's Latin (the product name, notation, a version) beside Noto's
Hebrew, because Archivo is not bundled in the browser either. When the kit
ships Archivo and the two Noto faces they reach the browser the way the CJK
subsets do (`:/fonts`, `kit::installBundledFonts()`), and
`tools/fonts/subset_cjk.py` is where the coverage gate is extended. Until then
the catalogue test that holds the three catalogues to their script's own
characters is what keeps a character the face lacks out of them.

## The language manager

`cube::i18n::LanguageManager` (`src/app/qt/i18n/language_manager.{hpp,cpp}`)
is ICL Forge's `LanguageManager`
(`apps/shared/preferences/src/language_manager.*`, itself Countdown Solver's)
ported to ids. It is the `LanguageManager` singleton of the `Cubeulator` QML
module.

A person chooses in Settings > Language: **Same as this device** first (with
the device's language named in itself), then the nine, each in its own name
and applied at once (`SettingsScreen.qml`, `settings.language.<n>`). The
language button on Home opens the same screen. There is no other place to
choose, and the pseudo-locale is not offered.

| | |
|---|---|
| start-up order | `CUBEULATOR_LOCALE` (a code, or `xx`), then the saved `language/code`, then the device, then English |
| the device | the first of `QLocale::system().uiLanguages()` the app has a language for; Traditional Chinese is not guessed at |
| the setting | `language/code`; absent means "same as this device" |
| `availableLanguages()` | `{code, name, rtl}`, English first, names in themselves; never the pseudo-locale |
| `deviceLanguage()` | `{code, name}` for the "Same as this device (%1)" row |
| `setLanguage(code)` | saves, installs the translators, sets the layout direction and default locale, retranslates the engine; false for a code the app does not have |
| `useSystemLanguage()` / `hasOverride()` | forget the saved choice / whether there is one |
| `preview(code)` | switches without saving and accepts `xx`: tests, the gallery, the tour |
| `currentLanguage`, `selectedLanguage`, `rtl`, `currentLanguageName` | what QML binds to |

What it adds to the family's: ids; English under every language; the default
locale (numbers and times follow the app's language); the device's *list* of
preferences; and it leaves the font to `Theme.qml`.

### The pseudo-locale

`CUBEULATOR_LOCALE=xx cube_app` shows every string accented, bracketed and 40%
longer: `[Scàn à cûbé ~~~~]`. A string cut off loses its closing bracket; a
string with no brackets never went through an id lookup. It is generated from
the English by `strings_to_ts.py` (so it cannot drift) and is checked for
length and brackets by the tests.

### Right to left

`Main.qml` mirrors the layout when `LanguageManager.rtl` is true
(`LayoutMirroring` on the screen loader, inherited down): rows and anchors
reverse, panes change sides, the back control and chevrons turn round
(`Icon.qml`).

**Never mirrored** (`accessibility.md`): the cube - the 3D view, `CubeView`, a
side's nine stickers - the camera picture, direction arrows and the words
*left*/*right*, notation, key names, version numbers. `CubeView.qml` sets
`LayoutMirroring.enabled: false` on itself and its children; the 3D cube is
not affected by layout mirroring at all, and a test proves it (below). A
component that draws something of the object in the hand does the same.

Known limit, until E3a: in the legacy screens a `Column` has no layout
direction, so its children keep the column's left edge in a right-to-left
language. Panes, rows, anchors, button order and chevrons do mirror; the kit's
`KitPage` is what finishes it.

### C++ that still words things

Controllers expose codes; QML turns them into text. One is named in the
plan:

- `DirectScan.cameraError` (`direct_scan.cpp`): the text is
  `cube::to_string(CubeError)` from `src/lib/include/cube/error.hpp`. Expose
  the enum's name (`camera_not_found`, `camera_start_failed`, ...) and word it
  in QML with `scan.camera.*`, which exist.

`AppState.elapsedLabel()` builds `mm:ss` from digits. Times are always left to
right, but the digits should be the language's: format with
`Qt.locale(Qt.uiLanguage)`. It is in `AppState.qml`, which E2a splits.

## What it does not do

- **It writes no reviewed translation.** E5 does. The catalogues of de, fr, es,
  ja, zh-CN, he, ar and yi hold a first draft (above); the English shows only
  under a string added after a draft.
- **It does not choose faces.** See the kit.
- **The legacy screens are converted only where the design has a string.** The
  settings the design removes (cube motion, shader
  style) and the Method statistic stay literal and are on the allowlist under
  the experience lane; E3a/E3d delete them.
- **Qt's own catalogue** (`qt_<code>.qm`: standard buttons, dialogs) is
  loaded where Qt ships one. It has none for Yiddish.
